# 基金运营工作台 V2：开发实施手册

> 本手册面向产品负责人、开发人员、测试人员和协助编码的 AI。它把总体架构、前端规范和后端规范转化为可执行的开发流程、工作包、测试门禁和发布检查表。
>
> 当前首要目标仍是用真实样本完成 NAV 第一阶段验收。架构演进不得扩大未经确认的业务范围。

---

## 1. 文档体系与优先级

### 1.1 配套文档

- `基金运营工作台_V2_业务需求与调研总纲.md`：业务事实、确认状态和范围依据；
- `基金运营工作台_V2_总体架构_改良版.md`：领域边界、核心原则和演进方向；
- `基金运营工作台_V2_前端架构与开发规范.md`：前端目标结构和实现规范；
- `基金运营工作台_V2_后端架构与开发规范.md`：后端模块、API、数据和安全规范；
- `第一阶段_开发落地与验收.md`：当前已经实现、待验收和生产前缺口；
- `托管解析适配器开发说明.md`：托管样本与解析器专项规范；
- `邮箱托管模板与可解析表头清单.md`：当前可解析边界。

### 1.2 冲突处理

发生冲突时按以下顺序处理：

1. 最新、明确记录的用户或业务负责人确认；
2. 合规、安全和租户隔离要求；
3. 业务需求总纲中的已确认决策；
4. 总体架构中的冻结原则；
5. 前后端开发规范；
6. 当前代码行为；
7. 原型、示例和未确认假设。

不得用旧原型覆盖最新确认，也不得因为当前代码已经这样实现就将未确认行为自动视为业务规则。

### 1.3 变更记录

影响以下内容的决定必须记录日期、提出人、确认人、适用范围和理由：

- 业务口径；
- 租户或权限；
- NAV 生效和反账；
- 产品生命周期；
- 材料保留和下载；
- 外部机构规则；
- API 不兼容变化；
- 数据迁移；
- 核心技术栈变化。

## 2. 当前阶段目标

### 2.1 第一阶段完成标准

选择：

```text
一家真实管理人
+ 一个经授权的只读邮箱
+ 一种真实 NAV 模板
+ 一种真实估值模板
```

完成以下闭环：

```text
应收
→ 邮件或人工上传
→ 原件归档
→ 产品/份额/日期识别
→ 解析
→ 校验
→ 自动确认或人工处理
→ 有效版本
→ 冲突和反账
→ 审计与原件追溯
```

### 2.2 第一阶段不因本手册扩大范围

不进入当前开发：

- 完整备案、开户和变更流程；
- 投资者中心；
- TA 核算；
- 完整估值；
- 交易下单；
- 底层划款；
- 全量材料中心；
- 外部通知平台；
- 微服务和 Kubernetes。

### 2.3 架构整理与业务开发的关系

架构整理只能做行为保持型改造，除非工作项同时具备已确认需求和验收标准。每个重构工作包必须证明：

- URL 或兼容入口未意外变化；
- 权限未放宽；
- API 响应未意外变化；
- 数据库内容未被破坏；
- NAV、冲突、反账和审计测试继续通过。

## 3. 本地开发环境

### 3.1 环境要求

- Linux 或 macOS；
- Python 3.12+；
- Node.js 22.13+；
- npm；
- 推荐安装 uv；
- Docker + Docker Compose，用于 PostgreSQL 专项测试和容器验证。

### 3.2 最简单启动方式

```bash
./一键启动.sh
```

可选：

```bash
./一键启动.sh --port 8001
./一键启动.sh --no-open
```

一键启动只管理本机 `runtime/development.db` 和 `runtime/archive/`。终端已有 `DATABASE_URL` 或 `ARCHIVE_DIR` 时会拒绝启动，以防误操作其他环境。

### 3.3 手动准备后端

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r backend/requirements.lock
uv pip install --python .venv/bin/python --no-deps -e backend
uv pip install --python .venv/bin/python 'pytest>=8,<10' 'httpx>=0.28,<1'
```

### 3.4 初始化本地数据

```bash
mkdir -p runtime
.venv/bin/alembic -c backend/alembic.ini upgrade head
.venv/bin/python -m app.cli bootstrap \
  --group '本地测试集团' \
  --manager '本地测试管理人' \
  --email 'developer@example.invalid' \
  --name '本地管理员' \
  --roles admin,operator \
  --download
```

密码只在终端隐藏输入，不写入命令、文档或聊天记录。

### 3.5 手动运行

终端一：

```bash
COOKIE_SECURE=false \
ALLOWED_ORIGINS=http://127.0.0.1:5173 \
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

终端二：

```bash
.venv/bin/python -m app.worker
```

只有明确需要连接已配置的测试邮箱时才使用：

```bash
.venv/bin/python -m app.worker --mail
```

终端三：

```bash
cd frontend
npm ci
npm run dev
```

### 3.6 本地数据边界

- 不导入真实生产数据库；
- 不使用真实投资者、邮箱授权码或银行账户；
- 托管文件必须脱敏；
- `runtime/` 不提交 Git；
- 重置前明确备份需要保留的本地样本；
- 不使用破坏性命令清空不明确目录。

## 4. 工作项进入开发前

### 4.1 Definition of Ready

业务功能进入开发前必须具备：

- 明确用户和业务问题；
- 需求编号及确认状态；
- 确认人和日期；
- 至少一个脱敏真实案例或样本；
- 正常流程；
- 异常和更正流程；
- 权限角色和管理人范围；
- 输入、输出及数据来源；
- 完成证据；
- 不在范围内的内容；
- 可执行验收标准。

缺少真实样本的解析需求不得宣称“已支持”。缺少口径确认的计算需求不得用合理猜测进入正式代码。

### 4.2 架构分类

开发前回答：

1. 它属于哪个管理人？
2. 核心主体是 Product、Investor、Party、Account 还是关系？
3. 它是 Business Case 还是 Data Operation？
4. 权威数据使用什么强类型模型？
5. 需要哪些 Document 和 Evidence？
6. 产生哪些 Event、Exception、Task、Decision 和 Audit？
7. 唯一性、幂等和并发键是什么？
8. 是否涉及敏感信息或下载？
9. 是否需要数据库迁移？
10. 如何证明不破坏现有 NAV 链路？

### 4.3 风险分级

| 等级 | 示例 | 最低验证 |
|---|---|---|
| 低 | 文案、非业务样式、无状态组件 | 前端测试、类型检查、构建 |
| 中 | 新查询、筛选、普通表单、解析器新模板 | 单元/集成测试、浏览器流程 |
| 高 | 权限、NAV 生效、反账、生命周期、文件下载 | PostgreSQL、并发、安全和浏览器验收 |
| 极高 | 数据迁移、证据模型、生产部署、密钥 | 备份恢复演练、迁移演练、发布审批 |

## 5. 分支、提交与变更范围

### 5.1 分支

建议一个工作项一个分支，名称表达目标，例如：

```text
codex/fe-router-foundation
codex/be-module-split
codex/nav-custodian-adapter
codex/data-expectation
```

不得在同一分支混合无关依赖升级、视觉重写和业务功能。

### 5.2 提交

每个提交应当：

- 目标单一；
- 可测试；
- 不包含真实数据和秘密；
- 不修改无关文件；
- 迁移和对应模型同提交或明确相邻；
- 行为重构与业务变化尽量分开。

### 5.3 处理已有修改

- 开始前检查工作区状态；
- 未经确认不覆盖他人或用户已有修改；
- 与当前工作重叠时先理解差异；
- 不使用 `git reset --hard` 或强制覆盖解决冲突；
- 自动格式化限定在本次修改文件，避免制造无关 diff。

## 6. 标准开发循环

```text
读取需求与架构
  ↓
检查当前代码、迁移和测试
  ↓
写/更新验收测试
  ↓
实现最小垂直切片
  ↓
运行针对性测试
  ↓
运行完整质量门禁
  ↓
浏览器走通关键流程
  ↓
更新文档和验收记录
  ↓
审查权限、数据和回滚风险
```

### 6.1 最小垂直切片

一个业务功能通常按以下顺序：

1. 业务规则和验收例；
2. 数据模型/迁移；
3. 领域规则；
4. Application Service 和事务；
5. 权限 Policy；
6. Request/Response Schema；
7. Router；
8. 前端生成类型和 Query；
9. 页面/表单；
10. 审计、事件和异常；
11. 自动化和手工验收。

不要先制作完整页面，再倒推后端和权限。

## 7. 前端开发流程

### 7.1 新增页面

1. 确认页面是否值得拥有独立 URL；
2. 在路由表登记路径、权限和标题；
3. 在 `pages/` 创建路由组件；
4. 在对应 `features/` 建 Query、Mutation 和领域组件；
5. 复用 `components/ui`；
6. 筛选和分页进入 URL；
7. 处理加载、空、403、404、409 和系统错误；
8. 添加路由和页面测试；
9. 检查刷新、前进后退和管理人切换。

### 7.2 新增 Query

- 使用集中 Query Key；
- Key 包含 managerId 和必要筛选；
- 使用生成的响应类型；
- 定义合理 staleTime；
- 只有活跃数据设置 refetchInterval；
- 4xx 不做无意义重试；
- 页面卸载后请求可取消。

### 7.3 新增 Mutation

- 明确成功后受影响的 Query；
- 金融数据、权限和生命周期不乐观更新；
- 提交期间防重复；
- 409 显示并发冲突并提供刷新；
- 422 显示业务原因；
- 成功提示区分归档、解析、确认和生效；
- 不使用全局“刷新所有数据”。

### 7.4 新增表单

- 使用可见标签；
- Decimal 保持字符串；
- 日期类型和时区含义明确；
- 前端限制与后端 Schema 一致；
- 错误可关联到字段；
- 高风险操作必须要求原因；
- 上传只表示归档，不暗示解析成功；
- Dialog 关闭后清理敏感草稿。

### 7.5 新增 UI 组件

- 先检查 `components/ui` 是否已有能力；
- 新原语优先 Base UI；
- 使用 Design Token，不散落色值；
- 支持键盘、焦点和 disabled；
- 状态不能只靠颜色；
- 组件不直接请求业务 API；
- 为复杂交互添加组件测试。

### 7.6 前端依赖

新增依赖前记录：

- 解决什么已出现的问题；
- 现有代码为什么不足；
- bundle 和维护成本；
- 是否与 Base UI/Tailwind 重复；
- 许可证和安全情况；
- 替换或移除路径。

结构调整阶段计划引入 React Router 和 TanStack Query；TanStack Table、Zustand、SSE 客户端均需满足触发条件。

## 8. 后端开发流程

### 8.1 新增 API

1. 确认所属领域模块；
2. 定义权限和对象归属；
3. 定义 Request/Response Pydantic Model；
4. 定义稳定错误码；
5. 在 Service 中实现事务用例；
6. 将唯一性和关键关联放入数据库约束；
7. 写 Audit/Event/Decision；
8. Router 只做 HTTP 适配；
9. 添加成功、权限、校验和并发测试；
10. 更新 OpenAPI 和前端生成类型。

### 8.2 新增 Service 用例

Service 接收：

- 当前数据库 Session；
- actor 或 system identity；
- 已验证的输入；
- 必要 Storage/Adapter 依赖。

Service 负责：

- 加载并锁定对象；
- 调用 Policy 和领域规则；
- 修改当前状态或追加版本；
- 创建 Exception/Task；
- 写 Event/Decision/Audit；
- 返回类型化结果。

Service 不创建隐藏 Session，不提交外层事务，不直接构造 HTTP Response。

### 8.3 新增模型

检查：

- 是否直接包含 manager_id；
- 是否需要组合外键；
- 是否需要唯一约束；
- 是否不可变；
- 是否有 current/effective 与 history 分离；
- Numeric 精度；
- date/timestamptz；
- revision；
- 索引是否服务真实查询；
- 是否误用 JSON 逃避建模。

### 8.4 新增权限

- 先定义业务动作，不直接新增角色判断；
- 更新领域 Policy；
- 明确管理人和产品范围；
- 增加拒绝测试；
- 验证跨牌照只读；
- 更新 `/auth/me` capability 或权限输出；
- 敏感下载单独测试和审计。

### 8.5 新增业务状态

- 画出允许的状态转换；
- 明确每条转换的权限、前置条件和 Evidence；
- 状态由 Service 修改；
- 非法转换返回 422 或 409；
- 状态变化写 Event 和 Audit；
- 不将可重复事项塞入 Product 生命周期枚举。

## 9. 数据库迁移流程

### 9.1 创建迁移前

- 检查最新 Alembic head；
- 对比 ORM 模型和实际 Schema；
- 确定迁移是否向后兼容；
- 估算表大小、锁和回填时间；
- 确认不可变 Trigger 是否需要扩展；
- 为迁移写升级测试。

### 9.2 标准步骤

```text
新增结构（Expand）
→ 部署兼容代码
→ 分批回填
→ 数量与业务值核对
→ 切换读取
→ 观察
→ 停止旧写入（Contract）
```

### 9.3 验证

至少验证：

- 空数据库从 0001 升到 head；
- 现有开发库从上一版本升级；
- SQLite 兼容迁移；
- PostgreSQL 真实迁移；
- 不可变 Trigger 仍存在；
- 外键和唯一约束生效；
- 回填数量和字段值正确；
- 旧应用版本是否能在短期兼容 Schema 上运行。

### 9.4 不可逆迁移

证据表或业务留痕迁移可以不提供破坏性 downgrade，但必须：

- 在迁移说明中明确；
- 发布前完成备份；
- 在隔离环境恢复演练；
- 保持应用版本回滚兼容；
- 不将“无法 downgrade”误认为无需回滚方案。

### 9.5 禁止

- 修改已发布迁移；
- 在迁移中连接外网；
- 未回填就增加 not null；
- 无验证删除旧列；
- 在生产直接使用 ORM create_all；
- 通过清空数据库解决迁移问题。

## 10. 后台任务开发

### 10.1 新增 Job

每种 Job 明确：

- kind；
- manager_id；
- payload Schema；
- dedup_key；
- 优先级；
- 最大重试；
- 可重试错误；
- 待人工错误；
- 成功产生的业务结果；
- Audit/Event；
- 监控指标。

### 10.2 Handler 要求

- 幂等；
- 一次处理一个有限工作单元；
- 长网络调用不占用长事务；
- 可在进程中断后安全重试；
- 不覆盖历史候选；
- 错误保存稳定 code，不泄露敏感内容；
- 单个 Job 失败不终止 Worker 主循环。

### 10.3 测试

- 重复执行不产生重复结果；
- 两个 Worker 不同时处理同一任务；
- Worker 崩溃后任务可恢复；
- 可重试和待人工错误正确分类；
- 原件在解析失败后仍可下载；
- 恢复后相关异常正确关闭并留痕。

## 11. 托管解析器开发

### 11.1 样本准入

- 来自明确托管机构和业务类型；
- 已脱敏；
- 保留结构、表头、合并单元格和公式特征；
- 至少包含正常样本；
- 尽可能包含多份额、反账、空字段和格式变体；
- 记录样本日期和来源确认人。

### 11.2 实现步骤

1. 使用检查脚本确认 Workbook/PDF 结构；
2. 定义识别特征，避免仅凭文件名；
3. 实现字段映射；
4. 使用 Decimal 和明确日期解析；
5. 输出候选及结构化错误；
6. 添加脱敏 fixture 测试；
7. 测试重复解析和重放；
8. 测试未知产品不自动建档；
9. 测试同值和冲突路径；
10. 更新模板清单和适配器说明。

### 11.3 解析器完成标准

- 对已声明支持的样本字段准确；
- 未支持变体明确进入人工处理；
- 不猜测空值；
- 不把单位净值变化冒充收益；
- 不直接生效越过业务校验；
- 能定位原始文件、Sheet 和行；
- 解析版本可追溯；
- 重放不覆盖历史。

## 12. 文件与材料开发

### 12.1 接收

- 流式读取并限制大小；
- 计算 SHA-256；
- 生成系统存储 key；
- 保存原文件名和媒体类型；
- 不信任扩展名；
- 数据库记录和解析 Job 在明确事务顺序中创建；
- 上传完成提示“已归档/待解析”。

### 12.2 下载

- 按 Document 所属 manager_id 重新授权；
- 混合产品文件要求更高范围；
- 校验哈希；
- 安全 Content-Disposition；
- 记录 Audit；
- 不暴露存储路径；
- 敏感文件不缓存。

### 12.3 逻辑材料

建设 Document/DocumentVersion/DocumentLink 时：

- 不破坏现有原件 ID；
- 相同字节不等于同一业务材料；
- 同一材料版本只存一次并可多处关联；
- Requirement、Document 状态、Submission 状态分开；
- Evidence 引用具体版本，而不是含糊引用文件名。

## 13. 金融数据规则

### 13.1 Decimal

- Python 使用 Decimal；
- PostgreSQL 使用 Numeric；
- JSON 使用字符串；
- 前端输入保持字符串；
- 不经过 float 或 JavaScript Number；
- 舍入规则由业务确认并集中实现。

### 13.2 NAV 版本

- 每条候选不可变；
- 同一份额和估值日可以有多个历史候选；
- 只有一个 EffectiveNav；
- 同值不同来源保留来源，不生成假冲突；
- 不同值生成冲突；
- 反账创建新记录并更新有效指针；
- 记录估值日与收到日期；
- 历史曲线使用当前有效版本但可查看全部版本。

### 13.3 计算展示

- 未确认口径不开发；
- 不跨份额盲目求和规模；
- 净值变化不等于投资者收益；
- 回撤口径和基准明确显示；
- 空值不显示为零；
- 每个指标能追溯数据版本和日期。

## 18. 回滚与事故处理

### 18.1 应用回滚

- 保留上一版本镜像和配置；
- Schema 采用向后兼容 Expand；
- 出现功能故障时先停止相关 Worker，避免继续产生错误数据；
- 回滚应用版本后验证读取和关键流程；
- 保留失败版本产生的 Audit 和 Job 记录。

### 18.2 数据问题

不要直接更新或删除不可变业务记录。处理顺序：

1. 停止继续写入问题领域；
2. 保存证据和受影响范围；
3. 判断是显示、有效指针还是候选数据问题；
4. 通过更正记录和 Decision 修复；
5. 必要时从备份恢复到隔离环境分析；
6. 经明确事故决策后才执行生产修复脚本；
7. 记录操作者、脚本哈希、前后数量和验证结果。

### 18.3 邮箱或解析事故

- 停用单个邮箱而非删除；
- 原邮件保持不变；
- 暂停对应 Parser 版本；
- 将受影响 Job 转人工复核；
- 修复后从原件重放；
- 不自动覆盖已经人工确认的有效 NAV。

### 18.4 秘密泄露

- 立即停用或轮换泄露凭据；
- 评估日志、提交和备份影响；
- 撤销相关 Session；
- 不通过删除审计记录隐藏事件；
- 记录影响范围和恢复动作。

## 23. 最终执行原则

后续开发始终遵守：

```text
真实业务优先于概念完整
数据正确优先于界面热闹
权限边界优先于操作便利
历史可追溯优先于原地修正
数据库约束优先于前端假设
垂直闭环优先于横向铺开
兼容迁移优先于一次性重写
可恢复优先于不可逆自动化
```

当一个技术或架构选择没有解决已经出现、可以测量的问题时，默认不引入；当一项业务规则没有真实案例和确认人时，默认不进入生产开发。
