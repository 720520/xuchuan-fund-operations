# 基金运营工作台：产品范围与核心规则

更新：2026-09-08。本文为唯一业务规则入口。整理前需求可在 Git 提交 `b87fe03` 的原《业务需求与调研总纲》中追溯；下表章节号均指该原文。

“沿用”表示原文已有明确确认，本次没有重新向用户确认；“建议”是本次整理提出的取舍，尚非已批准的范围变更。实现及验收状态另见[本地验收报告](本地验收报告.md)。

## 1. 产品只围绕两个结果建设

让运营少下载、少复制、少录入、少找材料；让关键结果能够查清来源、处理人、时间和历史变化。

近期服务本公司内部基金运营，先做好每日净值的收集、核对、归档与异常处理。托管等专业平台继续办理原有业务，工作台汇集结果与证据。长期全流程愿景保留，但不自动成为当前开发任务。

## 2. 日常流程

配置产品和份额的接收预期 → 只读收邮件或上传材料 → 自动保存原件、识别与校验 → 正常数据自动生效 → 人工处理异常 → 查看有效净值及来源。

人工主要处理缺件、未知产品、解析失败、校验问题、冲突和反账。系统应自动记录日常操作，避免为留痕再填一份重复台账。

## 3. 第一阶段范围

| 能力 | 沿用的范围 | 边界 |
|---|---|---|
| 产品台账 | 管理人、产品、份额、人工建档、新产品候选确认、生命周期 | 可登记简化备案并转产品；不建设完整备案审批 |
| 数据接收 | 同牌照多个邮箱、净值及其他邮件接收、人工上传、原件保存、历史附件导入 | 多邮箱和首批邮件分类已实现；规则需在真实试运行中校正 |
| 净值处理 | 模板解析、校验、自动确认、人工录入、冲突选择、反账版本 | 不猜测缺失值，不把收到日期当估值日 |
| 异常处理 | 当前牌照共享列表、直接处理、并发校验、处理留痕 | 无领取、释放、转派流程；只做站内提醒 |
| 查询 | 最新净值、规模原值、历史曲线、处理进度、来源与版本 | 数据日期和计算口径必须明确 |
| 估值字段 | 原文已确认仓位、持仓、现金、收益和回撤解析方向 | 样本与口径仍待验证；不等于自建估值或收益核算 |
| 权限与留痕 | 管理人边界、本人账号、独立下载授权、关键操作审计 | 不能因简化页面弱化隔离与历史保护 |

**收敛建议：**把完整持仓、收益口径及集团规模汇总列为独立验收项，先验每日净值闭环。它们原先包含在第一阶段方向中，本次不擅自取消；是否从第一阶段完成条件中移出，待业务负责人决定。

## 4. 唯一维护的核心规则

| 编号 | 当前规则 | 原文依据 |
|---|---|---|
| R01 | 管理人是数据和写入权限边界。同人可加入多个牌照，操作时明确目标牌照；其他集团默认不可访问 | §3.1、§3.2，8 月 31 日确认 |
| R02 | 同集团运营可查看其他牌照产品详情；未加入牌照不能写入。详情查看不自动授予原件、敏感材料或下载权 | §3.2，8 月 31 日后续修正 |
| R03 | 管理员拥有所属牌照全部角色页面及操作权限，审计使用本人账号；不扩张跨牌照权限 | §3.2，9 月 1 日最新确认 |
| R04 | 当前牌照成员均可查看并直接处理异常，提交校验版本防并发覆盖；无领取、释放、转派 | §3.2，9 月 1 日最新确认，覆盖旧 §17.1.2 |
| R05 | 未知产品先形成候选，由运营核对后正式建档；不凭模糊名称自动匹配 | §3.2 最新确认、§7；适配器说明 |
| R06 | 日频净值每个交易日接收前一个交易日的数据，15:00 为截止，未收到算迟到；本轮提供上交所 2025–2026 日历，牌照启用时核对适用性。原周频配置保留，是否存在例外产品待核对 | 2026-09-07 用户本轮确认，替代日频截止待定状态 |
| R07 | 管理人、产品、份额、估值日期明确；同份额同估值日只有一个有效版本。正常规则通过自动确认，重复值保留来源，冲突人工选择 | §9.1、§15；开发记录 |
| R08 | 人工补录标记实际账号，指定产品、份额和估值日，不要求第二人复核；仍需通过必要校验 | §9.1 BR-NAV-008；开发记录 |
| R09 | 反账手动标注并记录原因，新增记录且保留原记录；历史曲线使用新的有效值，收到日期另记 | §16；开发记录 |
| R10 | 原始邮件、附件、候选、历史版本和审计不因更正或归档而覆盖、删除 | §9.1 BR-NAV-004、§16；9 月 2 日确认 |
| R11 | 已清算需管理员填写日期、原因和依据；停止应收并关闭缺件异常、默认隐藏，保留历史。恢复需原因，应收另行确认启用 | §3.2，9 月 2 日最新确认 |

R04 是异常处理入口授权的已有决定，不推导为成员可修改全部产品或下载全部原件；相关业务动作和材料访问仍遵守对应权限。

异常解除必须有结果：缺件在匹配到材料后解除；解析失败在重解析成功或人工补齐并通过校验后关闭；冲突在选定有效值后关闭。校验问题需修正，允许业务接受的情况须记录原因；必填、权限和数据结构错误不能豁免。收到材料不代表净值已确认。

## 本轮补充：应收与邮件处理（2026-09-07）

**已确认：**一个牌照可有多个邮箱，希望同时接收处理净值以外的邮件；用户反馈当前模板基本可解析，这是业务反馈，不等于新增真实样本验收结果。

日频以交易日为单位，不能用“昨天”或仅跳过周末代替；例如周一应收上周五数据（假设两天均为交易日）。本轮实现为北京时间超过 15:00 判迟到；采用上交所 2025–2026 年日历，启用时核对适用性。其他市场日历不自动套用。

到下一个交易日仍未收到时，可能需要运营人员在托管平台操作补发邮件（2026-09-07 用户确认）。平台负责提示和保留处理记录，补发动作由人工在托管平台完成；不建设平台自动发信或自动操作托管平台。次日跟进时间由管理员配置，界面初始建议 09:00，启用时明确显示；该默认值不是用户另行确认的统一业务时点。人工记录“已操作补发”不等于邮件已收到，缺件仍应等对应材料实际到达后解除。

**首批处理边界（2026-09-08 已同意逐步落地）：**

| 邮件/数据情况 | 建议处理 |
|---|---|
| 已识别净值材料，产品/份额/日期唯一，必填与已启用校验通过，无冲突 | 自动生效并记录来源；迟到与否单独记录，不因迟到要求二次复核 |
| 相同净值重复到达 | 留来源，不重复生成有效值 |
| 净值冲突、未知产品、未知模板或校验异常 | 转人工判断；反账继续显式标注及说明 |
| 已识别为普通资料或通知 | 归档并关联适用牌照/产品；只有明确需行动的类型才生成待办 |
| 无法确定邮件用途 | 进入待分类；不能一律标为净值解析失败，也不能默认为无事可做 |

邮件收到、材料能否匹配预期、净值是否可用是不同状态。其他邮件到达不能解除净值缺件；净值材料已收到但解析失败应保留解析异常。本轮以保存的接收时间判断：邮件优先使用邮箱 INTERNALDATE，缺失时使用同步时间；上传和人工录入使用各自接收时间。无法识别归属的原件须经人工核对匹配后才解除缺件。

其他邮件种类较多，已按接入邮箱的实际标题、正文和附件归纳首批规则（2026-09-08）。确定性规则先覆盖净值估值、风险投监、申赎投资者、合同用印、安全提醒、对账数据、完成通知和营销信息；无法确定的内容保留为待分类。规则根据人工纠正继续收敛，不因邮箱接入扩大原件权限。产品开放日识别及日历联动暂缓，待业务口径确认后再设计。

## 5. 留痕做到什么程度

针对一笔净值，应能找到所属管理人、产品、份额和估值日，原始邮件/文件或人工来源，候选值与有效版本，以及谁在何时做了什么决定、原因和变化前后内容。

系统自动记录来源、时间、账号和变化；人工只在异常判断、更正等确需解释时补充原因。不要把每次正常接收都改成手工审批、签字或另建事项。

保留期限、适用材料清单、导出要求、管理员级防篡改和恢复要求仍待业务/合规负责人明确。这里整理的是产品留痕需求，不宣称已经满足全部监管要求，也不把旧文档的“永久保留”措辞当作已确认的法定期限。

## 资料整理框架（2026-09-09 首批单份整理已实现）

本轮已实现单份资料的人工整理闭环；批量处理、服务端分页、详情侧栏、版本分组和导出仍是后续方案。不要求先整理完历史资料才使用。

### 页面与最小流程

邮件接收/人工上传 → 原件保存 → 待整理 → 确认分类、日期和产品关联 → 检索、授权下载。

| 页面 | 用途 |
|---|---|
| 待整理 | 汇集尚未人工确认整理信息的资料；当前支持逐份分类和关联产品 |
| 全部资料 | 已支持按当前牌照、产品、类型、来源及文件名/标题筛选；服务端分页待补 |
| 产品详情的“资料”页 | 同一资料库按产品过滤，不再复制文件 |
| 资料整理弹窗 | 已支持标题、类别、业务日期/期间、说明和多产品关联；完整整理历史与版本关系待补 |

### 最小字段与分类

- 入库必须明确所属牌照：来自邮箱配置或上传时所选工作区；资料暂时不知道属于哪个产品也能保存。
- 系统自动保存原文件名、来源邮箱/邮件或上传账号、收到时间、文件指纹；保留原有目录路径作为导入来源信息，不自动把目录名当作分类结论。
- 人工整理只需确认资料类型和适用范围：管理人通用，或本牌照一个/多个产品；标题默认原文件名。备注、业务日期为选填，收到时间不能冒充业务日期。
- 当前类型：净值与估值、合同与协议、产品备案与变更、托管及账户材料、定期报告、风险与合规通知、运营处理凭证、其他资料。未人工确认时保持“待整理”。
- “仅留存”独立状态尚未实现；后续如启用，仍须可搜索和追溯，不等于删除，也不代表业务已完成。

### 原件、整理和业务分别记录

1. 原件不因改分类、标题或关联产品而重命名、移动或覆盖；整理信息单独保存，每次修改记录实际账号、时间和前后值。
2. 同牌照同内容可复用已有存储，重复接收仍保留每次来源；同文件名但内容不同不能自动覆盖。不同牌照不自动合并授权。
3. 文件内容变化作为新原件保存；用户明确关联后才组成版本组，选择当前版本须留痕。不同日期的净值表是不同期资料，不自动当作互相替代的版本。
4. 当前整理状态为待整理、已整理；“仅留存”待后续实现。净值是否有效和业务待办是否完成继续分别管理。确认分类不触发净值生效，也不直接关闭应收异常。
5. 先提供手动整理；后续依据真实邮箱样本增加分类建议。无法识别的普通资料不能直接报为净值解析失败，已识别净值材料保留既有处理链路。
6. 产品关联不自动扩大原件访问权；涉及多个产品的完整原件不能因有其中一个产品查看权就下载。跨牌照资料仍须按既有授权边界处理。

### 第一批交付与验收

第一批已完成待整理列表、单份分类与多产品关联、基础筛选和操作留痕。下一批补批量整理和服务端分页，再做资料详情、版本分组与材料导出；资料缺失检查、到期提醒、正文全文搜索/OCR、自动分类和通用审批暂不进入当前范围。

已验证未分类文件可入库、单份材料可关联多个产品、结果可再次修正、跨牌照关联和无权限操作被拒绝、原件及来源保持不变。重复内容、同名不同内容、批量操作逐项反馈、产品资料页与全库一致性及超出当前列表上限的检索，在对应功能开发时继续验收。

### 实际资料样本校准（2026-09-10）

本地“待整理”目录仅用于需求分析，尚未导入系统。目录共 419 个文件、约 1.3 GiB，分为个人投资者 240、产品投资者 58、机构投资者 34、季报 30、结算单 57。格式包括 PDF 211、图片 93、音视频 46、Excel 61，以及少量 Word、文本和压缩包。存在 22 组完全相同的重复内容，共 44 个文件；重复存储约 114 MiB。系统应复用相同文件内容，但保留每次来源和目录位置，不能直接丢弃重复记录。

样本说明当前“只关联产品”的模型不足。资料还需要关联管理人、个人投资者、机构投资者、产品型投资者、证券/期货账户和报送批次。投资者与账户先作为资料主体，不等于立即开发完整投资者管理、申赎核算或交易流程。资料分类改用两层：一级区分净值估值、投资者准入与适当性、合同及认申购、产品备案与变更、定期报告、账户与结算、风险合规、运营凭证；二级再区分身份证明、合格投资者证明、风险测评、税收声明、双录、认申购单、季度运行表、投资者信息表、月度结算单等。

季报样本不是单一文件：27 份 XLSX 共 174 个工作表，既有产品运行及净值表现，也有投资者信息、债券风险明细、填报说明、数据字典和隐藏模板。同一产品同一季度的多份文件应组成“报送批次”，分别保存文件角色、报告期和提交状态。结算单中的 30 份旧版 XLS 每份均包含 9 个固定工作表，最大样本约 1,768 行，适合按“账户 + 月份 + 结算单类型”组成连续序列，首期只提取索引字段，不直接把持仓和成交写入净值数据。

文件接收还需补三项边界：9 个音视频超过现有 25 MiB 上限，最大约 112 MiB，须提供大文件专用导入方式；24 个 `.png` 实际为 JPEG、2 个 `.jpg` 实际为 PNG、4 个 `.xlsx` 无法仅凭扩展名确认格式，服务端必须检查真实文件类型；PDF 最长样本达 341 页，预览和后续 OCR 必须异步、限额并与原件下载权限一致。

个人身份、联系方式、资产证明、风险测评和双录属于更敏感的访问范围。后续资料主体和分类落地前，不能把现有牌照级“原件权限”直接当作所有投资者资料的访问授权；列表、预览、下载、导出和批量操作均需单独校验敏感级别并记录访问。

## 6. 暂不进入当前开发

沿用原有边界：完整备案/开户/重大变更流程、完整投资者管理及签约流程、申赎核算、交易指令与审批、对外销售交付、公众号、自定义工作流与报表、多渠道通知、OCR/通用 AI 抽取。资料中心可以先保存和索引投资者及签约原件，但不据此自动生成投资者台账或业务结论。

架构资料中的 Business Case、Evidence、Event 等长期对象及前端整体改造是设计参考，不因出现在对象清单或工作包中就必须全量建设。已有能力继续保留；修复真实缺陷时按涉及范围改进。

## 7. 后续怎样增加需求

每项需求用一行说明即可：**真实场景 → 现在多做了什么/缺什么证据 → 最小改动 → 如何验收 → 状态与确认日期**。涉及权限、数据口径或历史保留时，再补专门规则。

优先处理能减少反复人工动作、避免漏收错认、缩短查证时间的问题。没有真实案例的扩展先留候选，不为补齐架构排期。

规则改变时直接更新本表，并记录“日期、旧规则、新规则、依据”；不在多份文件末尾追加“最新确认”。后续阶段与退出条件见[开发阶段](开发阶段.md)；建议不得冒充已有业务批准。
