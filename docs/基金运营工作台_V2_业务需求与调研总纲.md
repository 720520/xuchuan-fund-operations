| 状态 | 含义 |
|---|---|
| `待调研` | 尚未获得真实业务信息 |

# 第一部分：产品定义

## 1. 产品愿景

### 1.1 暂定定义

基金运营工作台面向私募证券投资基金管理人，统一管理基金产品、运营数据、业务资料和运营任务，并自动完成规则明确、重复发生的运营工作，将运营人员的工作重点从重复操作转变为异常判断与业务确认。

平台还应对产品备案、产品开户、重大事项变更等运营流程形成完整留痕，使每项业务能够回答：由谁发起、依据什么材料、经过哪些处理和审批、何时完成、最终结果是什么。

### 1.1.1 近期产品定位

近期首先建设本公司管理人内部使用的运营工作台。第一阶段只围绕每日净值的收集、核对、归档、异常和审计形成可实际使用的业务闭环。系统架构应保留未来复制给其他管理人、私有化部署以及同一集团管理多个关联管理人的能力，但第一阶段不以对外销售和交付为目标。

### 1.1.2 长期产品愿景

长期目标是逐步覆盖私募证券基金管理人的日常工作留痕，包括但不限于：

- 产品设立、备案、开户、运营、重大事项变更和终止；
- 净值、估值相关数据及异常处理；
- 投资者签约、适当性和存续期资料归档；
- 线下签约材料与电子签约材料的统一归档；
- 符合监管要求的交易指令、风控检查、审批和结果留痕；
- 面向管理层的产品运营、风险和工作进度视图；
- 面向监管检查的材料、数据、流程和操作记录追溯。

这里的“覆盖交易”暂定为交易指令及其风控、审批和结果留痕，不代表建设行情、组合管理或直接下单系统。交易模块不纳入第一阶段。

### 1.1.3 产品建设层次

```text
第一层：产品、净值、资料、任务和审计基础能力
  ↓
第二层：备案、开户、重大事项变更等运营流程
  ↓
第三层：投资者资料、签约材料和存续期服务
  ↓
第四层：交易等外围业务数据接入与管理人全流程留痕
  ↓
第五层：监管检查材料组织、检索、导出和证明链
```

上述层次表示演进方向，不代表已经确定的开发排期。

### 1.2 必须明确的价值目标

- [ ] 降低人工复制、粘贴、下载和重复录入次数；
- [ ] 降低净值、资料和报表处理中的错误率；
- [ ] 让每个异常和待办都有负责人、状态和处理时限；
- [ ] 让关键数据和文件可以追溯来源与历史版本；
- [ ] 让管理人员可以了解运营进度、风险和积压；
- [ ] 让业务数据可以被后续报表和流程重复使用；
- [ ] 让管理人实时了解自有产品的运营状态、关键数据、待办和风险；
- [ ] 对产品备案、开户、重大事项变更等流程形成完整操作与材料留痕；
- [ ] 对线下签约和电子签约形成的投资者材料统一归档并可追溯；
- [ ] 在监管检查时，可以按产品、事项、时间和材料类型快速组织证明材料；
- [ ] 评估是否向投资者开放公众号净值查询，并明确数据范围、确认机制和安全边界。

### 1.3 必须回答的产品问题

| 问题 | 当前结论 | 状态 |
|---|---|---|
| 首要客户是哪一类机构？ | 私募证券投资基金管理人 | 用户初步确认 |
| 首要用户是谁？ | 运营人员负责高频操作；老板查看全流程；基金经理、交易员及其他岗位按职责查看或处理 | 用户初步确认，待明确各角色权限 |
| 第一阶段解决的唯一核心问题是什么？ | 每日净值收集、核对和归档 | 用户确认 |
| 产品是机构内部系统还是标准 SaaS？ | 第一阶段仅供本公司内部使用，后续期望支持其他管理人 | 用户确认 |
| 是否需要私有化部署？ | 后续对外时可能重新部署至客户内网 | 方向确认，具体约束待调研 |
| 首个目标市场和司法辖区是什么？ | 暂定为中国境内私募证券基金管理业务 | 有假设，待合规确认 |
| 由谁决策、谁使用、谁验收？ | 管理层决策；运营人员高频使用；其他员工按角色使用；验收人待定 | 待确认 |
| 是否直接面向投资者？ | 未来可能通过身份认证后的公众号查看本人持有产品及收益；第一阶段不做 | 长期方向，方案待定 |
| 是否管理投资者信息与材料？ | 后续必须归档身份、银行卡、联系方式、风险测评及线下/电子签约材料，并核算投资、赎回和收益 | 用户确认，非第一阶段 |
| 是否覆盖交易？ | 后续记录交易指令、风控检查、审批与结果，以满足监管留痕 | 用户确认，非第一阶段 |
| 是否支持集团和多个管理人？ | 同一集团可能拥有多个名义独立的管理人，系统需要表达其归属并隔离各管理人及产品 | 用户确认，详细权限待定 |

### 1.4 首要目标客户

首要目标客户暂定为：**中国境内私募证券投资基金管理人**。

仍需进一步收窄客户画像：

- 管理规模和产品数量；
- 员工及运营团队人数；
- 自主管理还是大量业务外包；
- 当前使用的托管人、外包机构和系统；
- 是否有专职合规、风控、运营和 IT；
- 是否需要本地部署或严格内网运行；
- 当前主要依赖 Excel、邮件、共享盘还是已有系统；
- 监管检查和内部审计的频率及主要痛点。

其他基金或资管机构暂不作为 MVP 兼容目标，后续需单独评估业务差异。

### 1.5 暂定不在 MVP 范围

- CRM 与客户销售管理；
- 完整投资交易、订单和组合管理（长期可能接入交易数据或增加留痕能力）；
- 完整会计核算与估值引擎；
- 资金清算和支付；
- 全功能 BPM 或低代码平台；
- 在线 Office 文档编辑；
- 通用 AI Agent 平台；
- 全行业 ERP；
- 未经验证的自定义功能平台。

投资者公众号净值查询、电子签约、完整投资者关系管理、备案/开户/重大事项变更流程，均需要纳入需求调研，但是否进入 MVP 必须在每日净值主流程验证后单独决策。

### 1.6 已确认的业务背景

- 管理人可能拥有大量基金产品；
- 每只产品可能涉及多个账户，账户可能属于证券、期货或其他业务渠道；
- 净值主要由不同托管人通过邮件发送，邮件正文和附件格式不统一；
- 部分业务信息不能或不会通过邮件发送，必须允许管理人主动上传；
- 老板需要观察完整工作流程和当前进度，而不仅是查看汇总数字；
- 管理层关注产品净值、规模、仓位、收益与回撤，以及备案和开户进度；
- 规模、仓位等数据可能需要从估值表提取；
- 不同数据存在实时、T+1、T+2 等不同可用时间，不应使用一个统一的“实时”承诺；
- 监管检查可能以产品为主线，也可能从管理人整体角度要求材料；
- 关键业务必须形成过程和结论留痕；微信、电话和线下沟通暂不要求完整采集，但最终业务结论必须进入系统；
- 当前监管痛点包括临时找不到材料、不清楚事项由谁处理、产品资料不完整，以及交易所函件等重要事项未被及时发现和处理。

# 第二部分：用户、组织与职责

## 2. 用户角色

### 2.1 需要访谈的角色

| 角色 | 主要关注点 | 是否为 MVP 用户 |
|---|---|---|
| 基金运营人员 | 日常数据、邮件、资料、报表、异常 | 是，核心操作用户 |
| 运营负责人 | 本管理人全部产品的台账、分工、异常及进度 | 是 |
| 产品经理/产品负责人 | 产品设立、变更、生命周期 | 待确认 |
| 基金经理 | 所负责产品的净值、规模、仓位、收益回撤等数据查看 | 是，默认不能修改净值 |
| 财务/估值人员 | 估值、对账、净值数据 | 待确认 |
| 合规/风控 | 合规资料、审批、审计与风险；小型机构岗位可能由兼任或挂名人员承担 | 待确认 |
| 交易员 | 获分配产品的工作所需数据查看 | 可登录，第一阶段不开放交易操作 |
| 管理层/老板 | 查看产品关键指标、全部流程进度、异常和积压 | 是，管理视图用户 |
| 系统管理员 | 用户、角色、配置、集成 | 是，技术管理权限不自动包含业务修改权限 |
| 外部协作方 | 托管人、外包服务商等 | 待确认 |

### 2.2 每个角色必须了解的内容

- 每天、每周、每月、每季度和每年分别做什么；
- 每项工作由什么事件或时间触发；
- 输入来自哪里，输出交给谁；
- 使用哪些邮件、Excel、文件夹、微信群或其他系统；
- 哪些步骤最耗时；
- 哪些步骤最容易错；
- 哪些事项容易遗漏；
- 哪些操作必须请示或复核；
- 谁可以替班，如何交接；
- 哪些工作不能自动完成；
- 发生错误后如何发现和补救。

## 3. 组织与职责模型

### 3.1 已确认的组织关系方向

不能简单假设一个租户等于一个完全独立的公司。现实中可能存在：

```text
集团/实际控制或运营主体
  ├── 管理人 A（独立法律主体/租户边界）
  │     ├── 产品 A1
  │     └── 产品 A2
  └── 管理人 B（独立法律主体/租户边界）
        ├── 产品 B1
        └── 产品 B2
```

2026-08-31 用户确认：管理人作为租户和业务数据隔离边界，产品归属于具体管理人；集团表达关联关系，不自动获得跨管理人权限。管理人之间默认隔离，跨管理人访问必须逐管理人明确授权并审计，不能依靠共享管理员绕过隔离。

同一用户可以加入多个管理人，在各管理人内分别配置角色和产品范围；同一人可以兼任多个角色，但必须使用本人账户操作，不共享运营账户。集团管理层可查看经授权的汇总视图，普通员工默认在选定管理人的工作区操作；上传、修改和确认时必须明确显示当前管理人。

### 3.2 已确认的角色授权基线

| 角色 | 默认数据范围 | 默认操作边界 |
|---|---|---|
| 集团老板/授权管理层 | 经明确授权的多个管理人及产品 | 查看指标、流程和异常；不能默认修改净值 |
| 管理人负责人 | 本管理人全部产品 | 查看全流程、分配工作；重要业务操作单独授权 |
| 运营负责人 | 本管理人全部产品 | 维护业务台账、分配任务、处理净值冲突和反账 |
| 运营人员 | 同集团所有管理人（牌照）的产品详情均可查看，不要求逐产品分配查看权 | 仅在本人已加入并获操作授权的牌照内上传、录入、处理异常、选择有效净值和标记反账；同集团其他牌照仅可查看 |
| 基金经理 | 本人负责的产品 | 查看净值、估值表、持仓及相关进度，默认不能修改净值 |
| 交易员 | 分配给本人的产品 | 查看工作所需数据，第一阶段无交易操作 |
| 合规/风控 | 明确授权的管理人及产品 | 查看职责所需材料、流程和审计，后续审批单独配置 |
| 财务 | 根据具体职责单独授权 | 财务流程未明确前不默认开放全部业务数据 |
| 系统管理员 | 用户、权限、邮箱和系统配置 | 负责账户开通、产品权限分配、离职权限撤销及任务交接管理；不因此自动获得净值等业务数据修改权 |

2026-09-01 最新确认（覆盖上表中“管理员不自动获得业务权限”的旧结论）：管理员在其所属牌照内可以查看所有角色页面，并拥有这些页面的全部操作权限；跨牌照边界不变，审计记录始终使用管理员本人账号。

2026-09-01 最新确认：异常中心取消领取、释放和转派。当前牌照下所有成员均可查看并直接处理异常；提交采用版本校验防止并发覆盖，并记录实际处理账号。邮件解析识别到全新产品时不得自动写入正式产品台账，而是形成待确认产品，由运营核对后创建。产品还可人工创建，或先登记简化备案事项，在备案结束后转入正式产品台账；完整备案流程暂不实现。

2026-09-02 最新确认：产品采用生命周期状态管理，第一阶段支持运作中、清算中、已清算和已归档。管理员标记已清算时必须填写完成日期、原因并上传清算依据材料；系统停止该产品净值应收、关闭未到材料异常并从日常页面默认隐藏，但不得删除或覆盖历史净值、邮件、附件和审计记录。管理员可显示历史产品，填写原因后恢复运作；恢复后应收规则不自动启用，须另行确认。

岗位名称不直接等同于权限。查看、修改、下载分别授权，投资者敏感资料也必须单独授权，不因“老板”或“管理员”角色自动开放。兼任角色时，业务访问仍须落在已授权的管理人和产品范围内。

2026-08-31 用户确认：由管理员负责员工账户开通、产品权限分配，以及离职时的权限撤销和任务交接。管理员仅在获授权的管理人范围内执行这些管理操作，并记录权限及交接变更；交接具体流程仍待细化。

2026-08-31 后续修正：实际运营业务通常在托管平台完成，运营人员请假不影响现有业务开展。同集团所有运营人员均可查看集团内各管理人的产品详情，替代此前“运营人员仅查看本人分配产品”的默认规则。该访问通过集团归属及运营角色的明确授权策略实现，服务端仍校验集团、管理人和对象归属，不取消租户隔离，也不开放其他集团的数据。

第一阶段不将每只产品配置主运营负责人、协办或请假代理设为业务前置条件。系统内若存在未完成异常任务，离职交接仍由管理员负责；请假不自动触发业务交接流程。“产品详情可查看”不等于投资者敏感材料可查看、文件可下载或净值可修改，这些权限继续单独控制。

2026-08-31 用户确认的牌照边界：此处“牌照”按管理人业务主体理解，不作为法律概念定义。运营人员对同集团但本人未加入的牌照仅具有产品详情查看权，不能上传、录入净值、处理冲突或标记反账。一个账户可以加入多个牌照，管理员在各牌照内分别配置其成员关系和角色操作权限；加入某一牌照并不授予其他牌照的写权限。操作时必须校验目标牌照的成员关系及具体动作权限，不得将一个牌照下的角色权限沿用到另一个牌照。

示例：某运营仅加入牌照 A 时，可操作 A（按已授予的动作权限），可查看同集团牌照 B 的产品详情但不能修改。管理员将其加入 B 并授予运营操作权限后，该账户才可分别在 A、B 的工作区操作；对其他集团仍默认不可访问。

### 3.3 剩余待确认事项

需要确认：

- [ ] 一个用户是否可以属于多个部门；

## 5. 优先级方法

建议为每个业务事项计算：

```text
人工成本 = 发生次数 × 单次耗时 × 参与人数

候选价值 = 人工成本 × 错误风险系数 × 可自动化比例

实施优先级 = 候选价值 ÷ 实施成本
```

除评分外，进入 MVP 的事项必须同时满足：

- 有明确的首要用户；
- 有真实样本；
- 有稳定、可描述的业务规则；
- 可以形成完整闭环；
- 有可量化的现状基线；
- 能在一个可控周期内交付；
- 不依赖尚未建设的大量外围系统。

- 每条异常关联产品、份额、估值日期、原始材料和失败原因；未收到材料的异常关联接收预期，不伪造文件来源；
- 具有目标牌照操作权限的运营人员共同处理，不要求事先分配负责人；
- 开始处理时记录实际处理人，并防止多人重复处理同一异常；
- 完成时保留处理结果、处理人、时间和操作历史；
- 同集团其他牌照运营可查看产品相关异常，但未获目标牌照操作授权时不能处理；材料下载及敏感内容仍受独立权限约束；
- 老板首页只显示处理进度，不堆积技术错误；
- 接收截止时间按产品配置，截止前不标记迟到；超过截止时间标记迟到并显示持续时长，第一阶段仅在站内异常中心提示（见第 28 节）。

### 17.1.1 已确认的异常关闭条件

2026-08-31 用户确认采用以下机制：

| 异常类型 | 关闭或解除条件 | 留痕及边界 |
|---|---|---|
| 未收到 | 对应邮件到达或运营补传后，自动解除“未收到” | 必须关联到对应接收预期；后续解析问题单独保留，不代表整体处理已完成 |
| 解析失败 | 重新解析成功，或运营人工补齐所需数据并通过校验后关闭 | 保留原材料、失败原因及解析/补录结果 |
| 数据冲突 | 运营选定有效记录后关闭 | 保留其他候选记录、来源及选择操作历史 |
| 校验异常 | 修正后重新校验通过；或运营确认属真实业务数据、填写原因后接受 | 保留触发规则、处理结果和接受原因；业务接受不等同于技术校验通过，不豁免权限或必要数据约束 |

异常关闭必须对应实际处理结果，不允许仅点击“完成”而绕过处理条件。

### 17.1.2 已确认的释放与接手机制

- 处理中断时，允许运营释放自己占用的待办，供其他具有目标牌照操作权限的运营接手；
- 管理员可在其管理授权范围内转交待办，接收人必须具有目标牌照相应操作权限；
- 释放、转交、接手均保留操作人、时间及前后处理人；
- 保留此前已产生的处理记录，释放或转交不代表关闭异常；
- 接手后继续防止多人重复处理同一异常。

### 17.2 异常场景清单

- 未按时收到；
- 重复收到；
- 发件人不符合预期；
- 文件损坏、为空或带密码；
- 不支持的文件格式；
- 模板发生变化；
- 无法识别产品；
- 无法识别份额类别；
- 无法识别估值日期；
- 一封邮件包含多个产品；
- 文件数据与正文不一致；
- 同一产品同日值冲突；
- 波动超过阈值；
- 数据勾稽不一致；
- 更正数据晚于报表发送；
- 人工确认超时；
- 外部接口或邮箱不可用。

每个异常需要定义：异常级别、负责人、SLA、处理动作、是否阻断、关闭条件和升级机制。

# 第十部分：权限、安全与审计

## 31. 权限模型

2026-08-31 已确认：采用“管理人隔离 + 角色动作权限 + 产品数据范围”的第一阶段模型，角色基线见第 3.2 节。查看与修改、查看与下载、业务概况与敏感材料访问分别控制。关键操作、下载及授权变更留痕。

第一阶段不建设复杂部门层级、任意字段授权平台和通用审批引擎；后续敏感资料模块仍需落实独立授权。第一阶段人工录入不要求第二人复核，不因下面的长期职责分离要求改变已确认的净值流程。

权限至少包含四个维度：

```text
谁（用户/角色/部门）
可以做什么（查看/新增/修改/确认/导出等）
对什么对象（产品/净值/资料/任务等）
在什么数据范围内（租户/部门/负责产品/本人）
```

需要设计：

- 功能权限；
- 数据范围权限；
- 字段级敏感信息权限；
- 文件预览、下载和分享权限；
- 制单与复核职责分离；
- 临时授权和代理；
- 管理员与运维访问；
- 跨租户支持访问的审批和审计。

## 32. 多租户隔离

- 所有租户业务数据明确包含租户归属；
- 查询和写入在服务端强制校验租户上下文；
- 缓存、队列、对象存储和搜索索引同样隔离；
- 文件地址不能依靠不可猜测 URL 代替权限校验；
- 批量任务和后台任务必须携带租户上下文；
- 自动化测试必须覆盖跨租户越权；
- 备份恢复需要考虑单租户恢复需求。

## 33. 审计事件

关键审计记录至少包含：

- 租户；
- 操作人或系统身份；
- 操作时间；
- 动作；
- 对象类型与 ID；
- 修改前后值；
- 操作原因；
- 数据来源；
- 请求或任务关联 ID；
- 必要时记录 IP、设备和会话。

必须审计的候选操作：

- 登录和认证失败；
- 用户、角色和权限变更；
- 产品主数据变更；
- 净值确认、更正和作废；
- 文件上传、下载、分享和删除；
- 任务转派、关闭和取消；
- 报表生成、下载和发送；
- 邮箱和外部集成配置变更；
- 管理员或运维访问业务数据。

## 34. 安全与合规待确认项

- [ ] 适用的法律、监管规则和行业要求；
- [ ] 数据是否允许上云和跨境；
- [ ] 数据和审计日志保存年限；
- [ ] 个人信息和敏感业务信息范围；

- 服务时间和可用性目标；
- 计划维护窗口；
- RPO 和 RTO；
- 数据库、文件和配置备份频率；
- 恢复演练频率；
- 单租户误删除恢复；
- 邮件或外部服务中断后的补同步；
- 异步任务失败后的重试与死信处理；
- 系统降级和人工应急流程。

## 40. 可观测性

至少监控：

- 邮箱同步是否正常；
- 消息积压；
- 文件解析成功率和耗时；
- 外部集成错误率；

- 数据库和对象存储状态；
- 未按时收到的预期数据；
- 异常任务积压；
- 审计日志写入失败；

# 第十三部分：MVP 定义

## 41. 建议的 MVP 目标

建议将 MVP 明确定义为：

> 面向本公司私募证券基金管理业务，让运营人员能够按产品和份额建立每日净值接收预期，从不同托管邮箱接收或由管理人主动上传净值及估值材料，自动识别、解析和校验数据，对缺失、冲突、异常及更正进行人工处理，确认最终有效净值，并完整追溯原始邮件、上传文件、处理过程和修订历史。管理层和基金经理可以在各自权限内查看已确认的产品净值及处理进度。

## 42. 建议的 MVP 功能范围

### 必须有

- 登录与基础用户管理；
- 基础租户隔离；
- 管理人为租户、角色控制动作、产品授权控制数据范围；支持同人多角色及多管理人明确授权；
- 经授权的集团汇总查看；查看、修改和下载分开授权，权限变更与下载留痕；
- 产品、份额和负责人；
- 管理人人工创建产品，以及从邮箱附件解析产品信息（新产品创建确认机制待定）；
- 从空数据开始运行，支持上传历史或新增数据附件解析，不要求迁移 V1 数据库；
- 邮箱接入；
- 管理人主动上传，作为非邮件来源和人工补录入口；
- 原始邮件/文件留存；
- 选定模板的净值解析；
- 估值表中的仓位、持仓、现金、收益和回撤解析（字段和口径待样本核验）；
- 管理员维护预期发送开关与接收频率，包括周频；
- 运营人员直接录入净值并记录账户来源；
- 净值校验；
- 正常数据规则通过后自动确认，冲突由运营人员选择；
- 反账特别标注，原记录保留；历史曲线及收益回撤使用反账后的有效数据；
- 按牌照共享的异常中心：有权运营共同处理、开始时记录处理人并防止重复处理、完成后留痕；
- 人工修正与确认；
- 净值版本与来源追溯；
- 精简老板首页：最新净值、产品规模、净值历史、收益回撤曲线和今日处理进度；
- 关键操作审计。

### 可以后置

- 完整资料中心；
- 自定义工作流；
- 自定义报表；
- 复杂组织架构；
- 多渠道通知（第一阶段已确认仅站内异常中心及未处理数量提示）；
- OCR 和通用 AI 文档抽取；
- 大量外部接口；
- 租户自助配置所有规则；
- 移动端。

### 第一阶段明确不做

- 投资者公众号查询；
- 交易指令、风控审批和交易留痕；
- 对其他管理人销售、交付或提供在线服务；
- 投资者信息、签约材料、申购赎回和收益核算；
- 产品备案、开户和重大事项变更的完整线上流程；
- 自研完整估值核算引擎；估值表字段解析已纳入第一阶段，缺失字段的计算需求尚未确认。

## 43. MVP 前置条件

开发前至少获得：

- 3～5 位真实运营用户的访谈；
- 20～50 封脱敏真实邮件；
- 每类模板至少 5～10 个真实附件；
- 正常、更正、重复、错误和迟到样本；
- 现行人工操作流程；
- 净值校验规则和阈值；
- 角色与确认权限；
- 当前工作量和错误率基线。

## 44. MVP 业务验收指标

最终指标需以调研基线为基础确认。候选指标：

| 指标 | 当前基线 | MVP 目标 | 统计方式 |
|---|---:|---:|---|
| 单笔净值平均人工处理时间 | 待测 | 降低 60% | 系统事件与抽样 |
| 人工复制粘贴次数 | 待测 | 降低 80% | 流程对比 |
| 支持模板解析成功率 | 待测 | ≥ 95% | 真实样本集 |
| 产品/份额自动匹配准确率 | 待测 | ≥ 98% 或待确认 | 人工复核结果 |
| 异常自动建任务覆盖率 | 待测 | 100% | 异常测试集 |
| 关键操作审计覆盖率 | 待测 | 100% | 验收用例 |
| 跨租户访问阻断率 | 不适用 | 100% | 安全测试 |
| 原始来源可追溯率 | 待测 | 100% | 抽样检查 |

## 45. MVP 退出条件

只有满足以下条件，才能从 MVP 扩展到资料、报表或更多流程：

- 目标用户连续使用核心流程；
- 真实数据运行达到约定周期；
- 关键业务指标达到目标；
- 没有阻断性的安全和数据一致性问题；
- 异常处理和人工接管机制有效；
- 运营人员确认系统确实减少工作量；
- 产品负责人批准下一阶段范围。

# 第十四部分：用户研究计划

## 46. 访谈准备

每次访谈要求用户准备：

- 最近一个真实工作日的工作记录；
- 实际邮件、附件和 Excel 样本（脱敏）；
- 当前使用的文件夹结构；
- 当前报表模板；
- 最近发生的一次错误或遗漏；
- 最近一次需要请示或复核的案例；
- 当前任务交接方式。

## 47. 访谈问题

### 日常工作

1. 请从上班开始，按时间顺序描述昨天做过的事情。
2. 每一步使用了什么工具？输入从哪里来，输出交给谁？
3. 哪些动作需要下载、复制、粘贴、重命名或重复录入？
4. 哪些工作每天都会发生？哪些只在特定日期发生？
5. 如何知道一件事已经完成？

### 异常与风险

6. 最近一次出错是什么？如何发现、如何修复？
7. 哪些事情最容易遗漏？
8. 数据冲突时相信哪个来源？
9. 什么情况必须找负责人确认？
10. 如果负责人不在，流程如何继续？

### 净值

11. 每日预计收到哪些产品、哪些份额的数据？
12. 如何判断邮件或文件属于哪个产品？
13. 收到后具体检查哪些字段？
14. 什么波动或差异会被视为异常？
15. 更正净值如何处理，历史记录如何保留？

### 资料

16. 文件现在存在哪里，如何命名和查找？
17. 如何知道一项资料缺失或即将过期？
18. 同一文件有多个版本时如何判断哪个有效？
19. 谁可以查看和下载敏感资料？

### 管理与改进

20. 负责人如何知道团队今天还有什么没完成？
21. 哪三个步骤如果自动完成，价值最大？
22. 哪些步骤绝不能完全自动化？为什么？
23. 如果新系统只能先解决一个问题，希望解决什么？

## 48. 现场观察记录模板

| 时间 | 业务动作 | 输入 | 操作步骤 | 使用工具 | 输出 | 耗时 | 等待时间 | 错误/风险 | 需要协作 |
|---|---|---|---|---|---|---:|---:|---|---|
| | | | | | | | | | |

不要只记录用户描述，应尽可能观察其真实操作，并统计点击、复制、切换系统和等待次数。
