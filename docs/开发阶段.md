# 开发阶段与退出条件

更新：2026-09-11。依据[本地验收报告](本地验收报告.md)。以下为建议实施顺序，无虚构完成日期；每阶段结束按实际效果决定是否继续扩展。

## 阶段 0：核心能力已建立

已完成本地验证：产品/份额、收件归档逻辑、模板解析、人工补录、自动确认、冲突、反账、共享异常、权限、轻量投资者、投资者份额流水与托管快照、资料服务端分页筛选和基础审计。97 项后端及 3 项前端测试通过；另有 5 项数据库并发/迁移测试因本机未配置专用 PostgreSQL 测试库而按条件跳过。

此阶段达到“功能可用”，尚未达到“真实运营省时、正式部署可靠”。不再为补齐长期架构重新建设这些能力。

## 阶段 1：把每日净值跑顺——应收功能已完成本地开发，继续真实试运行

目标：每天自动处理正常数据，只让运营处理需要判断的问题。

本轮已实现：交易日应收、15:00 迟到、可配置的下个交易日跟进、停机补查、托管补发记录及收到材料/净值确认分离。管理员核对后启用；自动确认规则沿用原逻辑。

1. 选定一家管理人、一个已授权邮箱和现有真实净值/估值模板。先核对已归档样本与现有解析器，避免重复采集和适配。
2. 启用并验证已实现的应收检查：确认上交所日历适用、周频例外和次日跟进时间（初始建议 09:00）。实测 15:00 迟到及跨交易日跟进，“已补发”不能直接关闭缺件。
3. 用户反馈当前模板基本可解析，优先抽检并修复实际问题，不重新全量适配。首批邮件分类已落地：复用同牌照多邮箱，净值材料进入净值链路，明确风险、业务动作和安全提醒形成待办，其余成为接收记录或待分类；继续用真实邮件校正规则。首页已提供紧凑交易日/节假日月历，产品开放日联动暂缓。净值自动确认的细化边界仍待确认。
4. 连续试运行，记录人工耗时、补录/纠错次数和异常发现情况。

退出条件：建议覆盖至少连续 5 个工作日和一个周频截止；正常受支持数据无需逐笔确认，无未解决误匹配或静默覆盖，运营确认比原流程省时。统计包含补录、纠错和额外填表，目标比例由实测基线决定。

运行涉及真实资料前先落实阶段 2 中适用的访问、附件与备份保护；阶段编号不是推迟必要保护的理由。

## 阶段 2：把证据找齐、把运行守住

资料整理作为本阶段首个业务切片，首批单份整理闭环已完成：资料中心总览、服务端分页筛选、产品入口、分类与日期/期间保存、多产品关联、人工确认、版本冲突保护、解析分流和审计均已落地。2026-09-10 对本地 419 份实际资料做结构分析，并完成轻量投资者主体、跨产品关系、结构化基础/适当性字段、资料细类、来源原件、多银行账户、份额变动流水和托管持仓快照；证件号与账号加密保存，接口只返回掩码。上传时可直接按敏感资料关联投资者，投资者类邮件原件和附件也受同一权限保护。下一步顺序为：按真实托管模板预填份额字段 → 安全批量导入与真实文件类型检查 → 报送批次主体 → 批量归类和关联 → 原件详情与追溯 → 季报批次、结算单序列和材料导出。样本详情及边界见[产品范围](产品范围.md)。

目标：按产品和时间找到依据，系统故障后能够恢复。

- 资料分页与主体筛选已完成；继续补净值历史和处理记录的分页，并增加资料期间筛选及原件详情追溯。
- 批量导入先做预检清单：显示文件数、大小、真实类型、重复内容、无法读取和超限文件；用户确认后逐项入库并保留相对路径，不移动或改写源目录。大文件失败可重试，不能让整批回滚或静默漏件。
- 继续补齐报送批次主体和通用账户资料关系；已实施的个人、机构、产品型投资者、多银行账户及其敏感权限保持独立，个人身份、资产证明、风险测评及双录不能沿用普通产品资料的下载范围。
- 提供最小材料导出：原件、有效值和历史版本、操作人/时间/原因、文件清单与对应关系；继续检查下载范围并留痕，不误导出混合原件。
- 确认保存期限、必备材料与防篡改要求，落实数据库权限分离、HTTPS、附件扫描/资源隔离、备份与异机恢复、磁盘与任务故障提示。

退出条件：正常、冲突、反账各抽样一次，可找齐来源和过程；超出原列表上限的历史记录仍可查询；未授权导出被阻断；完成数据库、原件和必要配置/密钥的恢复演练并核对结果。具体保存和材料要求由业务/合规负责人确认。

这是检查材料可用性的验收，不把“存在日志”直接等同于“已满足合规”。

## 阶段 3：补充管理分析

目标：让管理层读到可解释、可核对的指标。

按真实估值表逐项接入持仓、现金、仓位，确认收益/分红口径和产品/份额规模去重后，再增加集团汇总。先使用原件披露字段，缺失显示缺失，不猜算、不重复加总。

退出条件：每个指标都有来源、日期、口径和样本比对结果；反账会更新受影响序列，不把单位净值变化标为投资者收益。

原需求已包含这些方向，阶段拆分不等于取消。是否将它们继续作为旧称“第一阶段”的整体完成条件，由业务负责人决定；执行时以本文件的具体交付名判断完成，避免混用阶段称谓。

## 阶段 4：按实际痛点扩展运营事项

候选：备案、开户、重大变更、资料归档，再考虑投资者、签约和交易留痕。每次只选一个高频或高风险事项，以“关联产品 + 材料 + 处理结论 + 时间/账号”做最小闭环。

进入条件：前面核心流程稳定；有真实案例，能明确节省哪一步或补齐哪项必要证据。没有案例不排期，不提前做通用工作流、低代码、多租户销售交付和全量对象模型。

## 每次迭代只维护一行

真实问题｜最小交付｜样本/验收方法｜负责人｜结果。涉及口径或权限变更时同步[产品范围](产品范围.md)。不再为每次迭代新建一套总纲、架构和实施手册。
