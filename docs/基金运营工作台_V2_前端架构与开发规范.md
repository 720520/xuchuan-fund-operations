# 基金运营工作台 V2：前端架构与开发规范

> 本文规定正式前端的目标结构、技术边界、页面组织、状态管理、权限展示、设计系统和测试要求。
>
> 本文以当前 `frontend/` 为实施基线，不要求为了采用新库重写已经可用的 NAV 链路。所有改造均应保持现有业务语义、权限和审计行为不变。

---

## 1. 目标与非目标

### 1.1 目标

前端应做到：

1. 运营人员可以快速判断今天应处理的事项和异常；
2. 用户始终知道当前管理人、产品、份额和业务日期；
3. 产品、NAV、材料、异常和审计之间可以稳定跳转和回到原位置；
4. URL 可以表达主要页面和筛选上下文，支持刷新、收藏和浏览器前进后退；
5. 服务端数据请求、缓存、失效、轮询和错误处理有统一规则；
6. 权限展示与后端授权语义一致，但不把前端隐藏当成安全控制；
7. 表格、表单、Dialog、Drawer、空状态和反馈采用统一组件；
8. 页面按领域拆分，避免继续扩大单个 `App.tsx`；
9. 新增模块时不破坏现有视觉语言和无障碍能力；
10. 可以通过自动化测试和浏览器验收证明功能没有回归。

### 1.2 非目标

当前阶段不追求：

- SSR、SEO、服务端组件或静态站点生成；
- 微前端；
- 同时引入多套 UI 原语库；
- 为简单表单提前引入复杂表单引擎；
- 将所有状态放入 Redux 或 Zustand；
- 通过前端代码实现真正的数据权限；
- 一次性开放尚未实现的 7+1 全部模块；
- 仅为追求“Claude 风格”重写已验收页面。

## 2. 当前基线与主要问题

### 2.1 当前技术基线

| 类别 | 当前选择 |
|---|---|
| 框架 | React 19 + TypeScript |
| 构建 | Vite 8 |
| 样式 | Tailwind CSS 4 + CSS 变量 +现有业务 CSS |
| UI 原语 | Base UI |
| 组件变体 | class-variance-authority |
| 类名合并 | clsx + tailwind-merge |
| 图标 | Lucide React |
| 图表 | Recharts |
| API | 自定义 fetch 包装和 `useResource` |
| 路由 | 当前由 `view` 本地状态切换 |
| 表格 | HTML Table 封装 |
| 测试 | TypeScript 检查、生产构建、少量 Node 测试 |

### 2.2 当前可继续复用的能力

- 已确认的暖白、陶土色、轻边框视觉语言；
- Button、Input、Dialog、Table 等基础组件；
- 同源 `/api` 请求和 HttpOnly Cookie 会话；
- 对 Decimal 字段使用字符串传输和格式化；
- 产品、份额、NAV、材料、异常和权限的现有交互；
- reduced-motion、键盘焦点和基础响应式布局；
- 正式前端不使用演示数据的原则。

### 2.3 需要解决的问题

1. `App.tsx` 同时承担会话、管理人选择、全部数据加载、全部页面和全部 Dialog 编排，继续扩展会增加回归风险。
2. 页面由本地 `view` 状态切换，URL 无法稳定表达页面、产品和筛选条件。
3. `useResource` 使用统一 revision 刷新，任意修改可能让多个无关接口重新请求。
4. 全局 15 秒轮询不能区分活跃任务和稳定主数据。
5. API 类型手工定义，后端 Schema 变化后容易产生前后端漂移。
6. 页面、领域组件、表单和基础组件的目录边界尚不完整。
7. 传统 CSS 与 Tailwind 并存但缺少明确的新增样式规则。
8. 复杂列表尚未形成统一分页、筛选和 URL 状态规范。

## 3. 技术决策

### 3.1 现在冻结

- React + TypeScript + Vite；
- 单页应用；
- Tailwind CSS + CSS Design Token；
- Base UI 作为无样式交互原语；
- Lucide 图标；
- Recharts 仅用于确有业务价值的图表；
- REST API；
- 同源 Cookie 会话；
- 后端作为权限和业务规则权威来源。

### 3.2 下一轮结构调整引入

#### React Router

用于：

- 稳定页面 URL；
- 产品详情和异常详情深链；
- 浏览器前进、后退和刷新恢复；
- 路由级代码拆分；
- 统一 404、无权限和错误边界。

#### TanStack Query

用于：

- 服务端状态缓存；
- 精确失效；
- 加载、错误、重试和取消；
- 按页面设置轮询；
- 分页和查询参数；
- 减少 `useEffect + fetch` 重复代码。

引入 TanStack Query 后，不再使用全局 revision 作为主要刷新机制。

### 3.3 触发后再引入

| 能力 | 引入触发条件 |
|---|---|
| TanStack Table | 至少一个列表需要服务端分页、排序、列显示或固定列 |
| Zustand | 同一 UI 状态被三个以上远距离组件共享，且不适合 URL/Query/Context |
| 表单库 | 出现多步骤、复杂条件、数组嵌套或大量跨字段校验表单 |
| SSE | 轮询造成明显负载，或业务要求秒级显示后台完成结果 |
| 虚拟滚动 | 单页必须渲染大量行且服务端分页无法满足业务 |

### 3.4 明确不采用

- Next.js，仅为内部 SPA 不引入 SSR 复杂度；
- Redux 作为默认状态容器；
- Radix UI 与 Base UI 同时作为基础原语；
- GraphQL，仅为接口形式升级复杂度；
- 在 localStorage 保存登录令牌；
- 将投资者敏感数据持久化到浏览器存储。

### 4.1 目录职责

- `pages/`：路由入口，只编排领域组件和页面级查询。
- `features/`：围绕一个业务能力组织查询、Mutation、组件和表单。
- `components/ui/`：无业务语义的基础组件，不直接请求 API。
- `api/`：传输协议、生成类型、Query Key 和错误模型。
- `lib/`：与 React 组件无关的纯函数。
- `layouts/`：登录布局、工作区外壳、侧栏和主内容区域。

### 4.2 禁止依赖方向

- `components/ui` 不得依赖 `features` 或 `pages`；
- 一个 feature 不得直接导入另一个 feature 的内部文件；
- 页面不得直接拼接不一致的 fetch；
- 生成的 API 类型不得反向依赖组件；
- 格式化函数不得读取全局 UI 状态。

## 5. 路由与信息架构

### 5.1 第一阶段路由

```text
/login
/m/:managerId
/m/:managerId/products
/m/:managerId/products/:productId
/m/:managerId/nav
/m/:managerId/documents
/m/:managerId/exceptions
/m/:managerId/exceptions/:exceptionId
/m/:managerId/audit
/m/:managerId/settings/members
/m/:managerId/settings/mailboxes
```

邮件归档和上传解析可以继续以导航入口存在，但路由上归属于材料或数据来源：

```text
/m/:managerId/documents/mail
/m/:managerId/documents/upload
```

### 5.2 后续路由

只有对应业务实际建设后才注册和显示：

```text
/m/:managerId/business-cases
/m/:managerId/business-cases/:caseId
/m/:managerId/institutions
/m/:managerId/investors
```

### 5.3 路由规则

- `managerId` 来自 URL，不再只存在于本地状态。
- 路由进入后必须用 `/auth/me` 返回的管理人范围校验。
- 当前管理人不可访问时显示明确无权限页面，不自动猜测并切到其他管理人。
- 用户主动切换管理人时，导航到目标管理人的对应首页。
- 产品、异常、材料详情必须同时验证对象归属，不能只信 URL 中的 managerId。
- 筛选、分页、排序和是否显示历史产品尽可能进入 URL search params。
- Dialog 是否进入 URL 由可恢复性决定：可分享的业务详情用路由；一次性编辑操作使用 Dialog/Drawer 本地状态。

### 5.4 页面标题和面包屑

- 浏览器标题包含页面名和产品/管理人上下文；
- 详情页必须有返回列表入口；
- 返回列表时保留原筛选和分页；
- 面包屑不重复侧栏，只表达当前对象层级。

## 6. 应用外壳与管理人上下文

### 6.1 Provider 顺序

建议：

```text
ErrorBoundary
  └─ QueryClientProvider
      └─ RouterProvider
          └─ AuthBoundary
              └─ ManagerWorkspace
```

不为每个领域建立全局 Context。Context 只用于稳定且低频变化的横切信息。

### 6.2 登录状态

- 应用启动读取 `/api/auth/me`；
- 401 进入登录页；
- 登录成功后重新读取 me，不手工构造用户对象；
- 收到全局 session-expired 信号时清理 Query 缓存并导航登录；
- 退出登录后清理全部管理人相关缓存；
- 不把会话令牌写入 localStorage、sessionStorage 或可读 Cookie。

### 6.3 管理人切换

- 当前管理人由路由参数决定；
- 切换前关闭未提交的一次性 Dialog；
- 有未保存表单时需要离开提示；
- Query Key 必须包含 managerId，防止不同管理人数据共用缓存；
- UI 始终在侧栏或页头清楚显示当前管理人；
- 跨管理人只读状态应在页面和操作区明确提示。

## 7. 服务端状态与 TanStack Query

### 7.1 Query Key 规范

```ts
export const queryKeys = {
  me: ["auth", "me"] as const,
  products: (managerId: string, filters: ProductFilters) =>
    ["managers", managerId, "products", filters] as const,
  product: (managerId: string, productId: string) =>
    ["managers", managerId, "products", productId] as const,
  nav: (managerId: string, productId: string, shareId: string) =>
    ["managers", managerId, "nav", productId, shareId] as const,
  documents: (managerId: string, filters: DocumentFilters) =>
    ["managers", managerId, "documents", filters] as const,
  exceptions: (managerId: string, filters: ExceptionFilters) =>
    ["managers", managerId, "exceptions", filters] as const,
};
```

规则：

- 租户数据的 Query Key 必须包含 managerId；
- 对象详情同时包含对象 ID；
- 筛选对象必须稳定序列化；
- 不使用页面中文标题作为 Key；
- Key 定义集中维护，不能在组件中随意拼接。

### 7.2 默认策略

- 认证错误不自动重试；
- 400、403、404、409、422 不自动重试；
- 网络中断和 5xx 可有限重试；
- 产品和成员等稳定主数据使用较长 staleTime；
- 活跃解析任务、邮箱状态和未解决异常可按页面可见性轮询；
- 历史审计、已归档材料不进行持续轮询；
- 页面隐藏时停止非必要轮询；
- 重新获得窗口焦点时只刷新需要新鲜度的查询。

具体秒数通过实际使用确定，不把所有接口统一设为 15 秒。

### 7.3 Mutation 与失效

Mutation 成功后只失效受影响的数据：

| 操作 | 应失效查询 |
|---|---|
| 创建产品 | 产品列表、工作台摘要 |
| 新增份额 | 产品详情、产品列表 |
| 补录 NAV | 目标 NAV、异常、摘要 |
| 选择有效 NAV | 目标 NAV、异常、摘要、产品最新值 |
| 上传材料 | 材料列表、解析任务、摘要 |
| 修改成员权限 | 成员列表；若修改当前用户则刷新 me |
| 切换产品生命周期 | 产品详情、产品列表、应收摘要、异常 |

不使用“所有查询全部刷新”作为默认策略。

### 7.4 乐观更新

金融数据、权限、有效版本和生命周期默认不做客户端乐观更新。必须等待服务器事务成功后再展示完成。

只允许对低风险、可轻易回退的纯 UI 偏好使用乐观更新。

### 7.5 轮询向 SSE 的演进

第一阶段继续使用精确轮询。满足以下条件之一再评估 SSE：

- 活跃页面轮询带来明显数据库或网络负载；
- 用户必须在数秒内看到解析完成、异常产生或邮箱恢复；
- 多用户协作需要及时提示版本已经被他人处理。

SSE 只发送失效提示和事件摘要，页面收到后重新查询权威 API，不把 SSE 消息本身当作最终业务状态。

## 8. API 客户端与类型

### 8.1 API 客户端职责

统一客户端负责：

- 自动加 `/api` 前缀；
- 使用 same-origin credentials；
- JSON 与 FormData 请求头；
- 解析统一错误响应；
- 401 会话失效通知；
- AbortSignal；
- 请求 ID 的接收和错误展示；
- 不记录密码、邮箱授权码和敏感响应正文。

### 8.2 OpenAPI 类型生成

实施顺序：

1. 后端为公开接口补全 request/response model；
2. 导出固定版本的 OpenAPI JSON；
3. 生成 `api/generated.ts`；
4. CI 检查重新生成后是否有未提交差异；
5. 保留一层业务友好的 Query Hook，不让页面直接依赖生成客户端的全部细节。

生成文件不得手工编辑。

### 8.3 数值协议

- 净值、金额、份额和比例通过 JSON 字符串传输；
- 前端输入期间保持字符串，不转为 JavaScript Number；
- 格式化只用于展示，不改变提交原值；
- 千分位、舍入和空值必须使用统一函数；
- `null`、空字符串和数值零必须区分。

### 8.4 日期协议

- 估值日和业务日期使用 `YYYY-MM-DD`；
- 系统时间使用 ISO 8601 带时区时间戳；
- 展示统一使用 Asia/Shanghai，除非将来允许用户配置；
- 不用浏览器本地时区推算上一估值日；交易日日历接入前明确显示当前算法边界。

### 8.5 错误协议

前端至少识别：

```text
401 未登录或会话失效
403 没有权限
404 对象不存在或不可见
409 并发冲突或唯一性冲突
413 上传超限
422 业务或字段校验失败
429 请求过多
5xx 系统错误
```

409 应提示用户刷新后查看最新状态，不能简单显示“保存失败”。

## 9. 状态归属规则

| 状态类型 | 存放位置 | 示例 |
|---|---|---|
| 服务端权威数据 | TanStack Query | 产品、NAV、材料、异常、成员 |
| 可分享页面状态 | URL | 当前页、产品 ID、筛选、分页、排序 |
| 单组件交互状态 | useState/useReducer | Dialog 开关、输入草稿、展开行 |
| 稳定横切上下文 | Context | 当前认证加载边界、主题（若有） |
| 少量跨树 UI 状态 | 满足触发条件后才用 Zustand | 全局命令面板、长期用户偏好 |

禁止把 Product、NAV、BusinessCase 等服务端对象复制进 Zustand 或 Context 形成第二份权威状态。

## 10. 组件系统

### 10.1 分层

```text
Base UI 原语
  ↓
components/ui 基础组件
  ↓
components/data-display / feedback 组合组件
  ↓
features 领域组件
  ↓
pages 页面编排
```

### 10.2 Base UI 策略

- 新的 Dialog、Popover、Menu、Select、Tooltip 等优先继续封装 Base UI；
- 不因示例代码流行而同时引入 Radix；
- 只有 Base UI 确实缺失关键能力且经过 ADR 评审，才考虑更换原语；
- 更换原语必须以组件封装层为边界，不让业务页面直接依赖原语库。

### 10.3 基础组件最低要求

- Button：主、次、幽灵、危险、链接及尺寸；
- Input/Textarea/Select：标签、帮助、错误、禁用；
- Dialog/Drawer：焦点管理、Esc、遮罩、标题和描述；
- Table：语义表头、空状态、加载和横向滚动；
- Badge/Status：状态颜色与文字同时表达；
- Alert/Toast：成功、警告、错误和操作反馈；
- Skeleton/Spinner：避免布局跳动；
- EmptyState：说明原因和下一步；
- ConfirmAction：危险或不可逆业务动作；
- FileInput/FilePreview：大小、类型、哈希和下载权限展示。

### 10.4 领域组件

领域组件可以知道 Product、NAV、Exception 等概念，但不直接决定权限。组件接收已经计算的 capability，例如：

```ts
<NavVersionActions
  canConfirm={capabilities.confirmNav}
  canReverse={capabilities.reverseNav}
/>
```

权限拒绝仍必须由后端完成。

## 11. Design Token 与视觉规范

### 11.1 Token 层级

```text
原始色值
  ↓
语义 Token：background / surface / text / border / primary / danger
  ↓
组件 Token：button / sidebar / table / status
```

业务组件不得散落新增十六进制色值。

### 11.2 现有视觉语言

- 暖白背景；
- 浅石灰侧栏；
- 深墨正文；
- 低饱和陶土色作为主要强调；
- 细边框优先于重阴影；
- 8pt 间距体系；
- 8/12/20px 圆角层级；
- 中文系统无衬线正文；
- 数字使用 tabular-nums；
- 动效 200–300ms，并支持 reduced-motion。

### 11.3 Tailwind 与 CSS 的边界

- 新基础组件和局部布局优先使用 Tailwind utility；
- 复杂工作台布局、跨组件状态选择器或无法清晰表达的样式可保留语义 CSS；
- CSS 变量统一放在 tokens.css；
- 不在同一个组件中重复用 CSS 类和 Tailwind 表达同一属性；
- 旧 CSS 在页面拆分时渐进迁移，不做无业务收益的全量转换。

### 11.4 状态颜色

颜色不能是唯一信息来源。每个状态同时显示文字或图标语义：

- 正常/完成；
- 待处理；
- 警告/临近截止；
- 错误/异常；
- 已失效/历史；
- 只读。

## 12. 页面模式

### 12.1 工作台

- 先展示今日待办、应收和异常；
- 指标必须标明业务日期和更新时间；
- 不跨份额盲目累加资产净值；
- 图表只回答一个明确问题；
- 空数据不显示虚构零值；
- 每张卡片可进入对应权威列表。

### 12.2 列表页

统一结构：

```text
页面标题与说明
主要操作
筛选和搜索
状态摘要（必要时）
数据表格
分页
空状态 / 错误状态
```

搜索输入应有防抖或提交动作；服务端分页后，查询参数全部进入 URL。

### 12.3 详情页

- 页头显示对象身份和当前状态；
- 关键指标显示来源日期；
- 主体数据、材料、事件和审计分区；
- 高风险操作放在明确操作区；
- 历史产品默认只读；
- 时间线是聚合视图，不代替各领域权威数据。

### 12.4 Dialog 与 Drawer

- 简短确认和少量字段使用 Dialog；
- 需要比较来源、查看上下文或多段内容使用 Drawer；
- 独立业务详情使用页面路由；
- Dialog/Drawer 关闭后焦点返回触发元素；
- 不在关闭后偷偷保留敏感表单值。

---

## 13. 表格策略

### 13.1 当前阶段

现有 HTML Table 封装继续用于简单列表。必须支持：

- 正确表头；
- 横向滚动；
- 空状态；
- 加载状态；
- 行级操作的可访问名称；
- 数字右对齐和 tabular-nums；
- 不在前端一次加载无限历史。

### 13.2 引入 TanStack Table 的条件

满足以下任意两项时引入：

- 服务端分页；
- 服务端排序；
- 多列组合筛选；
- 列显示和顺序偏好；
- 固定列；
- 行选择和批量操作；
- 同一表格存在多个业务视图。

TanStack Table 只负责表格状态和行为，视觉继续使用现有 Table 组件。

### 13.3 不做 Excel 克隆

可编辑网格、复制粘贴大区域、公式和树形聚合只有真实需求出现后才评估 AG Grid 等方案。默认表格不做单元格直接编辑，金融数据修改进入有校验和审计的明确表单。

---

## 14. 表单与业务输入

### 14.1 默认策略

- 简单表单使用受控或原生 FormData；
- 复杂表单达到触发条件后再引入表单库；
- 前端校验提升体验，后端校验才是权威；
- 422 错误应映射到字段或表单顶部；
- 提交期间防止重复操作；
- 成功后根据业务选择关闭、停留或进入新详情。

### 14.2 金融数值

- 输入使用字符串；
- 明确允许的小数位由后端 Schema 和领域规则决定；
- 不自动去掉用户尚未提交的小数点或尾随零；
- 展示格式化与提交值分开；
- 大金额不得经过 Number 中间转换。

### 14.3 文件上传

- 上传前显示文件名、大小和允许格式；
- 不承诺浏览器侧校验能够替代服务端限制；
- 上传完成只表示原件已归档，不表示解析和业务确认完成；
- 解析状态通过独立任务查询展示；
- 未识别产品不得在前端自动创建正式产品；
- 文件下载按钮必须根据服务端返回的能力显示，后端仍再次授权。

### 14.4 高风险操作

以下操作必须显示影响范围、要求原因，并等待服务端成功：

- 选择有效 NAV；
- 标记反账；
- 产品进入已清算或恢复运作；
- 修改用户权限；
- 下载投资者敏感材料；
- 完成或豁免业务事项材料。

---

## 15. 权限展示

### 15.1 Capability 模型

前端不直接散落 `role === "admin"`。由 `/auth/me` 和对象状态组合为 capability：

```text
canReadProduct
canEditProduct
canUploadDocument
canDownloadDocument
canConfirmNav
canReverseNav
canManageMembers
canManageMailboxes
canViewSensitiveInvestorData
```

### 15.2 展示规则

- 无页面访问权：路由级 403；
- 有查看权无操作权：显示内容并明确只读；
- 对象状态禁止操作：按钮禁用并解释原因；
- 敏感操作：未授权时不加载敏感数据；
- 后端返回 403 时不能因为前端曾显示按钮而忽略错误。

### 15.3 跨管理人

跨管理人查看时必须明显显示只读边界。切换管理人不继承前一管理人的操作 capability，也不复用不含 managerId 的缓存。

---

## 16. 加载、空、错误和反馈

每个页面必须分别处理：

1. 首次加载；
2. 后台刷新；
3. 空数据；
4. 无搜索结果；
5. 无权限；
6. 对象不存在；
7. 并发冲突；
8. 网络错误；
9. 系统错误。

首次加载可以使用 Skeleton；后台刷新不得清空已有数据。空状态说明为什么为空以及用户可执行的下一步，不使用虚构业务数据填充页面。

成功提示说明完成了什么，例如“原件已归档，正在等待解析”，不能笼统显示“操作成功”。

---

## 17. 可访问性与响应式

### 17.1 可访问性

- 所有输入都有可见 label；
- 图标按钮有 accessible name；
- Dialog 有标题和描述；
- 错误信息使用 `role=alert` 或合适的 live region；
- 键盘可以完成主要工作流；
- 焦点样式不能移除；
- 状态不能只靠颜色；
- 表格列头使用正确语义；
- 动画尊重 `prefers-reduced-motion`。

### 17.2 响应式

- 桌面是主要使用场景；
- 768–1024px 压缩侧栏和次要信息；
- 小于 768px 折叠侧栏，保证查看和简单处理；
- 复杂 NAV 比较和大型表格可以明确提示建议使用桌面；
- 触屏目标保持可操作尺寸。

---

## 18. 性能规则

- 页面级路由拆分后按路由懒加载；
- Recharts 等较大依赖只在需要图表的页面加载；
- 列表使用服务端分页，不依赖无限前端数组；
- Query 只失效相关数据；
- 避免每 15 秒刷新全部页面资源；
- 大文件不读入前端内存做无必要预览；
- 搜索和筛选请求可取消旧请求；
- 生产构建持续记录 bundle 大小变化。

暂不为了理论性能引入复杂 memo。先通过浏览器性能分析确认真实瓶颈。

---

## 19. 前端安全

- 不在浏览器存储会话令牌；
- 不渲染未经净化的 HTML；
- 文件名、邮件主题和解析内容按不可信文本处理；
- 前端路由守卫不代替服务端权限；
- 错误提示不展示邮箱授权码、服务器路径或堆栈；
- 敏感材料响应使用 no-store；
- 登出和会话失效时清空 Query 缓存；
- 不在 analytics、日志或错误上报中发送金融数据和个人敏感信息；
- 外部链接使用安全的打开策略并明确目标。

## 20. 测试策略

### 20.1 测试层级

1. 纯函数：Decimal 展示、日期、权限 capability、Query 参数；

## 21. 从当前 App.tsx 的迁移步骤

### FE-01：建立文件边界，不改变行为

- 提取 AppShell、Sidebar、ManagerSwitcher；
- 提取页面组件，但暂时继续由现有 view 状态调用；
- 提取 DialogHost 和反馈组件；
- 保持视觉和 API 请求不变；
- 对关键流程做浏览器回归。

### FE-02：引入路由

- 增加 React Router；
- 将管理人和页面写入 URL；
- 兼容旧根路径并重定向到用户首个管理人；
- 增加 403、404 和错误边界；
- 验证刷新、前进后退和详情深链。

### FE-03：稳定 API 合同

- 后端补 response model；
- 生成 TypeScript 类型；
- 逐步替换 `api.ts` 中手工响应类型；
- 保留自定义 API 错误和 Decimal 处理。

### FE-04：引入 TanStack Query

- 先迁移产品列表和产品详情；
- 再迁移 NAV、材料、异常；
- 最后迁移成员、邮箱和审计；
- 每迁移一组即删除对应 `useResource` 调用；
- 全部迁移完成后删除全局 revision 和统一轮询。

### FE-05：统一组件和 Token

- 将散落按钮、输入和 Dialog 替换为 `components/ui`；
- 将新增色值收敛到 Token；
- 逐页迁移旧 CSS，不全量重写；
- 完成键盘和响应式检查。

### FE-06：复杂表格按需升级

- 后端先提供分页和排序参数；
- 前端将查询状态放入 URL；
- 满足触发条件后引入 TanStack Table；
- 不改变金融数据的确认和审计流程。

## 22. 前端完成定义

一个页面或前端能力只有满足以下条件才算完成：

- 有稳定路由或明确的一次性 Dialog 入口；
- 正确显示当前管理人和业务日期；
- 使用统一 API 客户端和生成类型；
- 处理加载、空、错误、无权限和并发冲突；
- Mutation 精确失效相关查询；
- 不丢失 Decimal 精度；
- 后端权限拒绝能够正确展示；
- 关键操作有原因、影响说明和成功结果；
- 键盘和基本响应式可用；
- 测试、类型检查和生产构建通过；
- 相关业务文档和验收记录已更新。

---

## 23. 前端开发禁区

- 不在页面中直接复制新的 fetch 实现；
- 不在组件中用角色字符串代替 capability；
- 不将金额和净值转换为 Number 后提交；
- 不把服务端对象长期复制进全局 Store；
- 不为尚未实现的后端能力制作看似可用的正式入口；
- 不通过隐藏按钮声称实现权限；
- 不混用 Base UI 和 Radix 构建重复原语；
- 不一次性重写全部 CSS；
- 不用一个“完成”按钮消除不同类型的异常；
- 不在成功提示中混淆“已上传”“已解析”“已确认”“已生效”；
- 不使用真实客户、投资者、邮箱或账户信息作为测试数据。

## 24. 架构决策摘要

| 决策 | 结论 |
|---|---|
| 前端框架 | React + TypeScript + Vite |
| 渲染方式 | 内部 SPA |
| 路由 | React Router，下一轮引入 |
| 服务端状态 | TanStack Query，下一轮分批迁移 |
| 本地状态 | useState/useReducer，按需 Context |
| 全局 Store | 暂不引入 Zustand |
| UI 原语 | 继续 Base UI，不并行引入 Radix |
| 样式 | Tailwind + CSS Token，旧 CSS 渐进迁移 |
| 表格 | 当前 Table；满足条件后 TanStack Table |
| 表单 | 当前轻量方式；复杂表单出现后评估表单库 |
| API | REST + 同源 Cookie |
| API 类型 | 后端响应模型完善后由 OpenAPI 生成 |
| 实时 | 精确轮询；有指标后评估 SSE |
| 权限 | 后端权威，前端仅做展示和引导 |
